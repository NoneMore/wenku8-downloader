# 账号登录、独立浏览器验证与 CLI 会话交接

## Context

用户要求将 `wenku8 login` 改为账号密码登录，必要时自动打开浏览器完成验证并自动接收登录态，同时移除所有 CLI 手动 Cookie 导入入口。需求与验证范围见 [Change](../../specs/archive/native-account-login/spec.md)。

本次只读调查确认：直接 HTTP 请求登录页返回 Cloudflare 验证页；独立可见 Edge 能取得真实 GBK 登录表单，字段包括 `username`、`password`、`usecookie`、`action`，提交到同站 HTTPS `login.php?do=submit`。用户随后在独立终端完成真实账号登录，保存的会话通过新进程的账号页面验证与 CLI 详情查询；该次通过的传输为 Node。既有 CLI 使用 curl，HTTP 层原先直接拼接 Cookie 请求头，curl 不回收响应 Cookie，不能完整承担新认证生命周期。

## Decision

- 默认由终端接收账号密码，按取得的站点表单状态和 GBK 编码提交。密码仅留在本次认证内存中，不存储或通过进程参数传递；认证 POST 不自动重试。
- 需要人工验证时使用 Playwright 启动独立、非持久的可见 Chromium 浏览器上下文，优先使用本机 Chrome、Edge，再尝试已安装的 Playwright Chromium。用户正常完成验证，不操作日常浏览器资料，不引入防护绕过措施。
- 浏览器正常提交站点原生表单，自动读取本次上下文中的站点 Cookie 与 User-Agent；不通过默认浏览器回调、用户复制或扩展插件交接。
- Node 与 curl 共用 `tough-cookie` CookieJar，逐跳处理重定向与响应 Cookie，按域、路径、有效期和 Secure 属性发送会话。保留 HTTP 库的内部 Cookie 能力，CLI 移除手动导入能力。凭证提交及其重定向限定在已核实的 HTTPS 站点范围内。
- 以实际 CLI 请求访问账号页面并取得明确的已登录页面证据，作为持久化前的必要检查。分别尝试 curl 与 Node，保存通过检查的传输并供后续命令复用；不固定假定 curl 更适合验证后的会话。不能把浏览器成功页面或 Cookie 的存在等同于 CLI 会话可用。
- 在现有用户配置目录以版本化 `session.json` 保存程序管理的会话、User-Agent 与已验证传输，通过受限权限的临时文件和原子替换写入。认证写操作使用跨进程文件锁；响应更新检查会话 ID，防止旧请求覆盖另一登录或恢复已退出的会话。
- 不复用旧手动导入的用户 Cookie 文件；升级后需进行一次账号登录。浏览器上下文在所有退出路径关闭，不保存浏览器用户目录。`logout` 删除程序会话，保留业务数据。

## Alternatives

- **只支持直接 HTTP 账号登录**：依赖较少，但不能满足人工验证及自动接收登录态的要求。
- **只打开默认浏览器**：容易启动，但站点并未提供本工具已核实的会话回调协议，不能据此保证自动交接。
- **复用日常浏览器资料或要求手动开启远程调试**：引入对已有敏感资料的额外访问与配置，不采用。
- **将所有下载迁到浏览器传输**：扩大下载架构与运行依赖范围。当前选择先保留 CLI HTTP 传输并验证交接；若真实会话无法交接，应重新评估并更新 Change，不能暗中退回 Cookie 粘贴。

## Consequences

引入 Playwright 运行依赖，以及浏览器安装、图形环境和浏览器生命周期要求。普通下载复用保存的会话，不需要常驻浏览器。CI 需安装 Chromium，使用模拟站点覆盖真实浏览器交互，不依赖账号。

浏览器通过验证后，站点仍可能拒绝 CLI 的网络环境；此时明确失败，不发布可用会话的虚假结论。当前已取得 Windows + Edge 的真实账号登录与 Node 会话复用证据；这不代表所有平台、网络环境或验证码类型均已实站验证。其他路径仍需对应运行证据，不能由模拟测试替代。
