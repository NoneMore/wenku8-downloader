# 项目治理约定

本文是 wenku8-downloader 面向维护者、贡献者和编码 Agent 的**共享治理规则唯一入口**。使用与本地开发见 [README](../README.md)；当前模块地图见 [架构概览](architecture/overview.md)。

本仓库是 [Messiahhh/wenku8-downloader](https://github.com/Messiahhh/wenku8-downloader) 的 Fork。以下约定只适用于本仓库，不代表上游也采用这些规则。

## 一、代码优先的事实模型

- **Code first**：源码、实际配置和运行证据是判断**当前已实现行为**的主要依据；测试提供验证证据。文档、代码注释帮助解释实现，但不能把未实现的描述变成事实。
- **事实与目标分离**：设计和 Change 可以陈述将来要实现的目标。遇到文档、注释、代码或运行结果冲突时，先区分实际行为与期望行为，再在任务范围内修正或报告差异，不默认其中任何一方自动正确。
- **注释保留局部知识**：仅解释不明显且持久的约束、不变量、设计理由和接口语义；不重述直观代码。模块全局关系归 Architecture，重要历史取舍归 ADR。
- **避免重复权威**：不另建长期维护的细粒度“已实现功能规格库”；实施细节由代码与测试表达，变更中的要求保留在对应 Change 中。

## 二、从问题找到正确资料

| 要解决的问题 | 阅读入口 |
| --- | --- |
| 安装、运行、开发、测试 | [README](../README.md) 的用户使用和本地开发章节、`package.json`、CI |
| 理解当前模块边界 | [架构概览](architecture/overview.md)，并沿链接查看相关代码 |
| 确认具体行为及边界情况 | 源码、测试和必要的运行证据 |
| 了解某项正在推进的改变 | 相应的 `specs/active/<change-name>/`（如果存在） |
| 理解架构决策的历史理由 | 相应的 `docs/adr/`（如果存在） |
| 查找责任人、优先级、进度 | 项目实际采用的 Issue、PR 或任务跟踪工具 |

资料的阅读顺序不是权威顺序；普通改动不需要遍历所有 ADR 和 Change。

## 三、Architecture：当前架构知识

- 位置为 `docs/architecture/`，描述**现有**职责、依赖边界、主要数据流、关键约束与源码导航。
- 可记录方向性目标，但必须清楚标示为未实现的候选方向，不能混为当前事实。
- 仅在已经实现的模块边界、关键数据契约、重要用户行为等有实质改变时同步更新。
- 不逐行复制实现细节，也不在架构文档复述 ADR 的历史辩论；具体行为看源码与测试。

## 四、ADR：重要架构决策的历史

ADR 只用于保存**日后代价较高、难以从代码反推**的重要架构决定的背景、备选方案和取舍。例如长期影响持久化兼容性、接口边界或安全模型的决定。普通缺陷修复、简单功能调整和常规依赖升级无需 ADR。不能依据现有代码猜测历史原因并伪造追溯性 ADR。

- 发生实际决策时才创建 `docs/adr/0001-short-title.md`，后续使用递增编号与 kebab-case 名称。
- 推荐结构：标题、`Context`、`Decision`、`Alternatives`、`Consequences`；按需记录适用范围和相关实现链接，不要求状态字段。
- 若新 ADR **完全或部分替代**旧 ADR，只在**新 ADR 中向后**列出被替代的编号、范围与原因；不改写旧 ADR 来指向未来，不追加反向状态。
- 旧 ADR 可移至 `docs/adr/archive/`，即使只是部分被替代也可以归档；现行已实现架构结果始终应体现于 Architecture。
- ADR 不能代替实现证据，也不是对每个 PR 的强制许可环节。

## 五、Change：围绕变更意图组织工作

Change 是一个有边界、彼此相关的**变更意图**，不是任务、单个 PR、固定流程阶段或其他 Change 的子项。一个 Change 可跨多个任务或 PR；不同意图可独立管理。小范围修复不需要 Change。

- 正在推进的材料放在 `specs/active/<change-name>/`，不再推进的放在 `specs/archive/<change-name>/`；名称使用清晰的 kebab-case。
- **没有必备文件**：按需使用 `spec.md`（需求、边界与验收条件）、`design.md`（候选设计与取舍）、`tasks.md`（有价值的任务拆解或依赖）。只创建实际有内容的文件。
- `active` 只代表仍在推进，不保证已经批准或已准备实施；`archive` 只代表不再推进，可能是完成、取消、搁置或被替代，不证明代码已实施或文档仍适用。
- 活跃 Change 的规范稳定下来后，在原 `spec.md` 中更新，不需要保留多份过时的阶段副本。归档的规格保留历史，不随未来代码变化同步。
- 任务负责人、进度、优先级等易变状态保存在正在使用的跟踪工具中；`tasks.md` 仅在分解和依赖有价值时创建，避免维护两份状态。
- Change 可能触发 ADR（重要长期决策），实现完成后可能触发 Architecture 更新（已实现结构）；这是三项不同活动，不会自动互相生成。Git、PR、测试和 CI 保存实现与验证证据。

## 六、工程工作流和完成标准

1. 识别修改范围，判断是否需要 Change；普通任务直接处理。
2. 按问题阅读相关开发说明、架构地图、源码与测试；仅在历史取舍相关时查阅 ADR。
3. 修改代码时补充必要的回归测试，尤其关注解析、网络错误、恢复、图片与 EPUB 完整性。
4. 通常执行 `pnpm check`（typecheck、lint、test、build）；涉及 EPUB 输出时关注 EPUBCheck 对应 CI 测试。发布前可执行 `npm pack --dry-run`。
5. 通过 Git 提交和 PR（如使用）记录变更及实际验证结果；需要时链接 Change / ADR，**不强制填充不相关资料**。
6. 已实施的高层行为改变后更新 Architecture；产生重要长期决策时建立 ADR；Change 不再推进时按实际原因归档。

本仓库 `.github/workflows/ci.yml` 已配置 push / PR 检查。服务端分支保护、必选检查和审批要求须另行在 GitHub 配置；此文档**不能代表这些门禁已启用**。

## 七、代码库特有的兼容性与风险边界

以下是现有实现的重要检查点，不是永久禁止重构；若有意修改，应明确目标并通过相应测试验证：

- **恢复与数据格式**：`src/storage/schema.ts` 当前 Manifest 版本为 `1`。`BookWorkspace` 管理资源状态和持久化写入。更改 schema、缓存复用、路径或写入方式时须评估既有工作区与中断恢复。
- **章节与图片完整性**：`Downloader` 在章节下载失败后阻止继续生成；`EpubBuilder` 默认执行完整性校验。`--allow-missing-images` 是显式放宽检查的选项，改动失败语义需评估兼容性，避免静默输出意外缺失的内容。
- **站点边界**：页面结构和编码差异优先封装在 `src/site/`；并以离线解析测试覆盖，避免在 EPUB / 存储中散布站点 HTML 逻辑。
- **网络约束**：`src/http/` 统一处理限速、重试、429 冷却和传输。变更认证与重试策略时应评估站点限制、可观察错误及安全风险。
- **凭证与版权**：Cookie 和真实下载内容不进入源代码、测试样例、PR 或公开日志；遵守来源站点条款和适用法律，不把规避站点防护当成普通修复方案。
- **EPUB 约束**：变更资源引用、图片规范化、ZIP 打包或文档构建逻辑时，维护现有测试与 EPUBCheck 验证能力。

## 八、Fork 与上游同步

- 上游代码和提交是同步时的重要证据，但 Fork 的规则由本仓库维护。
- 同步前识别本地差异；同步后重点回归 CLI、Cookie、Manifest 恢复、图片与 EPUB 产物，必要时更新当前 Architecture。
- 上游同步本身不强制创建 Change 或 ADR；只有独立的重大意图或长期技术取舍才需要。
- 若计划独立发布、调整许可证、仓库归属或贡献权限，单独确认元数据及法律要求；不要只按当前 `package.json` 推断。

## 九、最小维护原则

`docs/adr/`、`docs/adr/archive/`、`specs/active/` 和 `specs/archive/` 仅在有真实内容时建立目录。不用空占位、虚构历史 ADR 或重复文档证明治理已经“完整”。

**模型有效的验收标准**：人类贡献者能从 README 找到治理入口，能从 Architecture 快速定位代码，能准确判断何时需要 ADR / Change，并能用现有测试和 CI 验证变更。
